# RAG 知识库核心原理 — 学习笔记

> 从零搭建 RAG 知识库的过程中，通过 Socratic 对话梳理的核心概念。

---

## 一、什么是 RAG？

**RAG = Retrieval-Augmented Generation（检索增强生成）**

类比：律师回答客户问题时，不会全凭记忆，而是**先翻案卷找到相关段落，再结合自己的理解给出答案**。

```
用户提问 → 检索知识库 → 找到相关片段 → 注入 AI 的 prompt → AI 生成答案
```

| 缩写 | 全称 | 含义 |
|------|------|------|
| **R** | Retrieval | 检索（翻案卷） |
| **A** | Augmented | 增强（把找到的内容塞给 AI） |
| **G** | Generation | 生成（AI 结合内容给出答案） |

## 二、核心原理：五层理解

### 第1层：表示层 — 文字变向量

**核心思想**：每句话可以变成一串数字（向量），意思相近的句子，数字也相近。

类比：地图上每个地点有经纬度坐标。北京 (39.9, 116.4) 和天津 (39.1, 117.2) 坐标很近，所以它们在地图上也挨着。

```
"镜头往前推"  → [0.12, -0.34, 0.56, ..., 0.78]  (1024个数字)
"推镜/Dolly"  → [0.11, -0.33, 0.55, ..., 0.77]  (1024个数字)
"今天天气真好" → [0.89, 0.12, -0.45, ..., 0.23]  (1024个数字)
                ↑ 前两句的数字很接近，第三句差很远
```

**为什么是 1024 个数字？**
因为一句话的"意思"比一个地点复杂得多：
- 维度 1~100 可能捕捉"主体"（镜头、人物、场景）
- 维度 101~200 可能捕捉"动作"（推、拉、摇、移）
- 维度 201~300 可能捕捉"方向"（前、后、左、右）
- ...每个维度捕捉一个"语义特征"

**关键概念：Embedding 模型**
- 就是把文字变成数字的"翻译器"
- 不同模型 = 不同的"坐标系"
- bge-large-zh：1024 维，中文口语理解强
- text-embedding-3-small：1536 维，OpenAI 出品
- **向量不能混用**：用 bge 建的索引，不能用 OpenAI 的模型来查询（坐标系对不上）

---

### 第2层：比较层 — 算距离找相似

向量之间可以算**余弦相似度**（cosine similarity），范围 0~1：
- 1.0 = 完全相同
- 0.8 = 非常相似
- 0.5 = 有点相关
- 0.0 = 完全无关

```
"镜头往前推"  vs "推镜/Dolly"     → 相似度 0.78 ✅ 高
"镜头往前推"  vs "摇镜/Pan"       → 相似度 0.52 ⚠️ 中
"镜头往前推"  vs "今天天气真好"    → 相似度 0.05 ❌ 低
```

**这就是 RAG 检索的基础**：用户提问 → 向量化 → 和知识库里的所有向量算距离 → 返回最近的几个。

---

### 第3层：存储层 — 向量数据库

**问题**：普通数据库（MySQL/SQLite）按关键词精确匹配，不理解语义。

```sql
-- MySQL：精确匹配
SELECT * FROM knowledge WHERE content LIKE '%推镜%';
-- ❌ 用户说"镜头往前推" → 搜不到

-- 向量数据库：语义匹配
collection.query(query_texts=["镜头往前推"], n_results=5);
-- ✅ 找到"推镜/Dolly"——因为语义相似
```

**ChromaDB 是什么？**
- 一个轻量级向量数据库
- 负责两件事：**存**向量、**找**最相似的向量
- 本地文件存储，无需部署服务器

**索引加速（HNSW）**

100 万个向量逐个算距离太慢。ChromaDB 用 **HNSW（分层可导航小世界图）** 索引加速：

```
第1层（粗筛）：把 100 万个向量分成 100 个"区域"
              用户提问 → 先判断在哪个区域 → 只搜这一个区域

第2层（细筛）：这个区域里再分 10 个小组
              继续缩小范围

第3层（精确）：小组里逐个算距离 → 找到最近的 Top-5
```

类比：找人先找城市 → 再找区 → 再找街道 → 最后找门牌号。不用全国挨家挨户敲门。

---

### 第4层：检索层 — 分块与查询

**分块（Chunking）**

长文档不能整篇向量化——太长了，语义太杂。要切成小段：

```
一篇 5000 字的文档
    ↓ 按 500 字/块切割
10 个 chunk，每个独立向量化
```

| 分块大小 | 优点 | 缺点 |
|---------|------|------|
| 太小（100字） | 检索精准 | 丢失上下文，AI 看不懂 |
| 太大（2000字） | 上下文完整 | 检索不精确，噪音多 |
| **合适（300-800字）** | 平衡精准度和上下文 | — |

**查询流程**

```
用户输入"镜头往前推，贴近人物情绪"
    ↓
1. 向量化：bge-large-zh 把问题变成 1024 个数字
2. 搜索：ChromaDB 用 HNSW 索引找最近的 Top-5
3. 返回：推镜/Dolly（78%）、变焦/Zoom（65%）...
```

---

### 第5层：注入层 — RAG 的最终目的

检索结果不是直接展示给用户，而是**注入到 LLM 的 prompt 里**：

```
System Prompt:
  你是 OPC 创作助手...
  用户当前配置：风格=水墨画，运镜=未选择...

  ## 相关知识库参考（由 RAG 检索）
  ### [camera_motion] 推镜 / Dolly（相似度: 78%）
  推镜 / Dolly：镜头沿轨道前后移动，推进制造压迫感，后拉制造疏离感...
  口语问法：镜头往前推进贴近情绪；像走进场景一样的推进...

  ## 可用运镜库
  基础运镜: 定机(Locked Down)、摇镜(Pan)...
```

**效果**：AI 不再瞎猜，而是基于精准的知识库内容回答。

## 三、我们项目中的 RAG 架构

```
OPC 创作助手 (OpcAgentChat.tsx)
    │
    ├─ 用户提问："镜头往前推，贴近人物"
    │
    ├─ [ragRetrieve()] → http://localhost:5000/rag/retrieve
    │   ├─ bge-large-zh 向量化
    │   ├─ ChromaDB 相似度搜索
    │   └─ 返回 Top-5 结果
    │
    ├─ [formatRagContext()] → 格式化为文本
    │
    ├─ [buildOpcSystemPrompt()] → 注入 system prompt
    │
    └─ [streamChat()] → 发给 LLM 生成回答
        │
        └─ 消息底部显示"📚 参考了 3 条知识：推镜 78%..."
```

## 四、关键概念速查表

| 概念 | 一句话解释 |
|------|----------|
| **Embedding** | 把文字变成一串数字（向量）的过程 |
| **向量（Vector）** | 一串浮点数，表示文字的"语义坐标" |
| **余弦相似度** | 衡量两个向量"方向有多像"的指标（0~1） |
| **ChromaDB** | 轻量级向量数据库，存向量 + 搜相似 |
| **HNSW** | 向量索引算法，不用逐个算就能快速找最近的 |
| **分块（Chunking）** | 把长文档切成小段，每段独立向量化 |
| **Top-K** | 返回最相似的 K 条结果 |
| **阈值（Threshold）** | 相似度低于这个值的结果不要（过滤噪音） |
| **bge-large-zh** | 中文专精的 embedding 模型，1024维 |
| **降级（Fallback）** | RAG 服务不可用时，系统仍能正常工作（只是没有知识增强） |

## 六、参数配置与微调指南

### 当前参数全景

一共 **7 个可调参数**，分布在 3 个文件中：

#### `retriever.py` — 检索参数

| # | 参数 | 当前值 | 行号 | 作用 |
|---|------|--------|------|------|
| ① | `top_k` | **5** | 第47行 | 每次检索返回几条结果 |
| ② | `score_threshold` | **0.3** | 第47行 | 相似度低于这个值的结果丢弃 |
| ③ | `query prefix` | `"为这个句子生成表示以用于检索相关文章："` | 第67行 | 查询前缀，bge 模型建议加 |
| ④ | `hnsw:space` | `"cosine"` | 第41行 | 距离算法（余弦相似度） |

#### `ingest.py` — 入库参数

| # | 参数 | 当前值 | 行号 | 作用 |
|---|------|--------|------|------|
| ⑤ | `chunk strategy` | **整行/整条目** | 第20-130行 | 分块策略（每条知识=一个chunk） |

#### `rag-client.ts` — 前端参数

| # | 参数 | 当前值 | 行号 | 作用 |
|---|------|--------|------|------|
| ⑥ | `topK` | **5** | 第32行 | 前端请求的返回条数 |
| ⑦ | `timeout` | **3000ms** | 第41行 | 请求超时时间 |

---

### 逐个参数详解

#### ① `top_k` — 返回几条结果

| 调整 | 效果 | 适用场景 |
|------|------|---------|
| 3 | 更精准，但可能漏掉好结果 | 知识库小、查询明确 |
| **5（当前）** | 平衡 | 通用 |
| 10 | 更全面，但可能引入噪音 | 知识库大、查询模糊 |

**调法**：`retriever.py:47` 改默认值，或前端调用时传参：
```python
retrieve(query, top_k=3)  # 改这里
```

#### ② `score_threshold` — 相似度门槛（影响最大）

| 调整 | 效果 | 适用场景 |
|------|------|---------|
| 0.5 | 严格过滤，只保留高相似度 | 查询明确，不想要模糊结果 |
| **0.3（当前）** | 宽松，允许弱相关 | 口语化查询多，宁可多不可漏 |
| 0.1 | 几乎不过滤 | 调试用 |

**调法**：`retriever.py:47` 改默认值：
```python
retrieve(query, score_threshold=0.5)  # 改这里
```

**建议**：先用 0.3 跑一段时间，看返回结果质量。如果发现太多不相关的结果，提到 0.4 或 0.5。

#### ③ `query prefix` — 查询前缀

```
当前："为这个句子生成表示以用于检索相关文章："
```

bge-large-zh 官方建议的检索前缀。**知识入库时没加前缀，查询时加了前缀**——让查询向量更偏向"检索"方向。

| 调整 | 效果 |
|------|------|
| 去掉前缀 | 查询和入库更对称，但检索精度可能下降 |
| **保持当前** | ✅ bge 官方推荐 |

**调法**：`retriever.py:67` 改字符串。

#### ④ `hnsw:space` — 距离算法

| 算法 | 适用场景 |
|------|---------|
| **`cosine`（当前）** | ✅ 文本语义相似度，最常用 |
| `l2` | 欧几里得距离，适合图像特征 |
| `ip` | 内积，适合已归一化的向量 |

**不建议改**。余弦相似度是文本检索的标准选择。

#### ⑤ 分块策略 — 最值得调的参数

当前是**整条入库**（每条知识=一个 chunk），因为你的知识库是结构化表格数据，每条本身是完整语义单元。

如果以后加入**长文档**，需要分块：
```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 每块 500 字
    chunk_overlap=50,    # 相邻块重叠 50 字（避免切断语义）
    separators=["\n\n", "\n", "。", "；", " "]  # 中文分隔符优先
)
```

| chunk_size | 效果 |
|-----------|------|
| 200 | 太小，丢失上下文 |
| **500** | 通用推荐 |
| 800 | 长文档适用 |
| 1500+ | 太大，检索不精准 |

#### ⑥⑦ 前端参数

```typescript
// rag-client.ts 第32行：返回条数（和 Python 端的 top_k 保持一致）
topK: number = 5

// rag-client.ts 第41行：超时时间
signal: AbortSignal.timeout(3000)  // 3秒
```

| 调整 | 场景 |
|------|------|
| 超时改 5000ms | RAG 服务偶尔慢（首次加载模型时） |
| 超时改 1000ms | 要求极致响应速度 |

---

### 建议的调参顺序

```
1. 先调 score_threshold（影响最大）— 决定"什么算相关"
2. 再调 top_k（影响中等）— 决定"给 AI 看几条"
3. 其他参数保持默认
```

### 快速调参实验

```bash
# 启动 RAG 服务
npm run rag:start

# 用不同参数测试同一个查询
python -c "
import sys; sys.path.insert(0, 'rag-service')
from retriever import retrieve

query = '镜头往前推'
for threshold in [0.3, 0.5, 0.7]:
    results = retrieve(query, top_k=3, score_threshold=threshold)
    print(f'\n--- threshold={threshold} ---')
    for r in results:
        print(f'  {r[\"score\"]:.0%} | {r[\"metadata\"][\"name_cn\"]}')
"
```

## 七、下一步可以深入的方向

| 方向 | 内容 |
|------|------|
| **分块策略优化** | 500字 vs 1000字，按段落 vs 按语义 |
| **混合检索** | 向量检索 + BM25 关键词检索，两者融合 |
| **重排序（Reranking）** | 检索 Top-20 后，用 Reranker 精排到 Top-5 |
| **RAG 评估** | 用 Recall@K、MRR 等指标量化检索质量 |
| **RAG vs 微调** | 什么时候该用 RAG，什么时候该微调模型 |
| **查询改写** | 用户问得模糊时，先让 LLM 改写成更适合检索的查询 |
